# Backend rules

These rules describe our standalone-only application. HUDIY_STANDALONE=1 is set by our native launcher to enable local Pi integrations. HUDIY_PROJECTION_HOST is ignored; no licensed Hudiy bridge, API client or original configuration reader remains in production source. Without our native launcher, the desktop backend keeps Pi controls unavailable.

## API boundary

- HTTP binds to 127.0.0.1:8766. Host/origin values are limited to the configured local app/preview ports. Action bodies are at most 4096 bytes; unexpected fields, arbitrary commands/URLs/paths and unsupported actions are rejected. The same-user local application is the trust boundary, not a public web account.
- GET status/projection/bluetooth/phonebook/display/wireless/audio-route/audio-settings exposes bounded local status. A running renderer is distinguished from a connected phone and decoded video frames. Wi-Fi keys, pairing keys and arbitrary D-Bus object paths are not HTTP data.
- The native command channel is user-only Unix IPC under the private state directory, at most 65536 bytes per newline JSON message. Only allowlisted screen routes, connection/media actions, options, validated audio-dsp settings, wireless reload and application exit are accepted.
- Static responses set CSP, nosniff and no-referrer. Selected local files use browser blob URLs. There is no cloud database, login provider or external backend policy to update.

## Preferences and projection

- Private JSON preferences use atomic replacement, 0600 mode and fsync before acknowledgement on Linux. Layout contains only known shortcut/order IDs and retains Dashboard, Applications and Android Auto. Browser edits wait for Pi hydration. Appearance preferences remain local to the web profile.
- refresh-settings accepts integer musicRefreshSeconds 1–60 and contactsRefreshSeconds 5–3600, rejecting booleans/fractions/strings/extra keys. Values persist in updates.json and apply to actual refresh work. Native connection checks run every five seconds independently of the UI interval.
- projection-settings accepts only boolean autostart/taskbarVisible/darkMode and Common/Day/Night. Options are sent to our process, then saved; disk failure resends previous options. Manual opening and automatic opening remain separate from phone background data.
- Changing taskbarVisible stops the current session to renegotiate video/touch geometry. The app remains running. One bounded handoff is scheduled after disconnect; failed saves or unrelated appearance changes do not trigger it. Fullscreen AA hides only our taskbar while projection is visible.
- Android Auto Quit stops admission until manual USB/Wi-Fi/Resume. Resume can retrigger our existing Bluetooth wireless connection. These requests do not pair phones, start media playback or prove a successful projection; later connected/frame status and screenshots provide that evidence.
- Explicit USB/Wi-Fi chooses that transport rather than reusing an unrelated active session. USB reconnect resets only a uniquely identified Android accessory, never an arbitrary hub or device; it runs in one owned worker, waits for phone initialization, and has a 15-second cooldown. It may interrupt that phone's projection.
- Explicit USB closes only our wireless bootstrap socket and rejects new wireless handoffs until Wi-Fi is selected. Other Bluetooth phone/OBD services and the saved hotspot preference remain available.
- The audio-input protocol descriptor remains stable when microphone hardware is absent. Actual capture requests return failure unless a real supported device opens. Status exposes microphoneAvailable and videoReady; a protocol handshake alone does not establish decoded video.
- application-quit accepts no arguments, asks our owned native process to exit and prevents further IPC commands while closing. Native teardown closes session/audio/pages and its owned Python backend. It does not reboot the Pi, erase settings or disable autostart. Outside the Pi application, unavailable hardware actions return 501.
- Physical brightness accepts 5–100%, uses the single actual kernel backlight with existing user permission and saves the choice. Day/Night controls the AA sensor independently of physical brightness.

## Bluetooth and phone

- Device discovery uses one powered adapter, validated current BlueZ paths and at most 128 entries. Discovery is explicitly requested, bounded to 30 seconds and released on stop/shutdown. Public device flags include paired, connected, SPP, A2DP receiver and PBAP phone support.
- Our Agent1 handles fresh numeric confirmation/cancel or explicit 0000/1234 PIN selection, with a 30-second prompt timeout. One pairing worker runs at a time. Successful explicitly requested pairing sets Trusted; automatic reconnect never pairs or trusts devices.
- Connect/Disconnect accepts only a currently paired address. Disconnect requires confirmation and removes its reconnect preference. Remove requires confirmation and a known currently paired device; real pairings are not removed during automated tests.
- bluetooth-autoconnect accepts a paired uppercase address and boolean enabled. At most 16 selected addresses persist privately. Retries are bounded to once per device every 30 seconds. Android Auto settings expose this same choice for PBAP phones independently of automatic projection opening.
- Wireless Profile1 owns only its registered profile and connection, requires a paired device plus enabled hotspot, and limits handoff frames to 4096 bytes. The protected AA listener binds to 192.168.12.1:5277. Bluetooth setup in the native protocol confirms only devices already paired through BlueZ; no silent AA pairing is performed.
- Phonebook uses owned BlueZ PBAP/OBEX sessions with bounded downloads, temporary files, RAM cache and disconnect invalidation. Contacts, Favorites and Call log keep phone order and use touch filters. No contact export is persisted to Git/cloud.
- Bluetooth media controls target exactly one current connected paired phone's addressed AVRCP player, with bounded D-Bus calls. Android Auto media uses our input channel only while connected. Caller-supplied paths, URLs and arbitrary media methods are rejected. Reported metadata is not proof that an external Spotify playback device updates the phone live.
- Calls use the matched oFono HFP service, fixed Dial/Answer/Hangup/Mute methods and validated number/call state. Dial requires confirmation. Device/network/audio changes refuse active calls where implemented. Automated tests use mocks; new real call or playback tests need explicit authorization.

## Required OBD and optional audio/network

- OBD selection accepts only a currently paired Serial Port adapter and RFCOMM channel 1–30. Our worker owns the direct socket; failed connections retry at most every 30 seconds. Fixed ELM initialization and read-only Mode 01 PIDs supply load, coolant, RPM, speed, throttle and voltage. Stale readings/history clear on disconnect. BLE-only adapters and arbitrary ECU commands are unsupported.
- Manual Bluetooth reading retains required automatic reconnection. Manual Stop suppresses that worker for the current session; serial/USB selection takes precedence. Simulated data is explicitly marked and never counted as vehicle evidence.
- wireless-hotspot requires boolean enabled and confirmed true, and waits until calls end. It switches only the fixed hudiy-recreation-car NetworkManager profile, updates next-boot autoconnect, privately saves our SSID/key/gateway settings and reloads our listener. Commands are argument arrays with timeouts; network/save failure attempts the previous mode. The app stays running. First-time protected AP preparation uses our separate normal-user installer; it creates an inactive profile and private settings, then runtime activation uses this existing control. A home router is not needed for car use; fresh-image service setup is still unverified.
- Optional audio-radio-output saves only a current paired A2DP receiver address or an empty choice, excludes PBAP phones and refuses active calls. Selecting it neither pairs nor starts playback. The route worker manages only our native PID or the single connected phone's playback streams, can set the default sink and never moves unrelated active streams. It waits during calls and verifies the route on a subsequent poll.
- Local-file equalizer/balance affect that browser file. Native AA PCM uses our independent 15-band processor and stereo balance; mono channels ignore balance and bands above their Nyquist limit. A separate audio worker retains partial writes with a bounded one-second raw mailbox per channel, one processed chunk of at most 8,192 bytes and a separately requested 100 ms sink buffer; diagnostics expose only numerical queue/drop/state counters. FM, CarPlay/Autobox, Bluetooth AVRCP DSP and multichannel fade/subwoofer audio remain incomplete. No audible-radio success is claimed without hardware evidence.

Native process/BlueZ profile registration and fixed NetworkManager switching replace the old runtime API integration. These are local OS integrations; no new external backend rules are needed. Standard OS service provisioning and privileges remain prerequisites on a fresh Pi. See SECURITY.md and STANDALONE.md for verified limits.

## Native projection audio settings

- GET `/api/audio-settings` distinguishes saved settings, runtime availability and native acknowledgement (`applied`). POST `audio-settings` accepts only a `settings` object containing equalizer, balance and/or a known preset. Exactly 15 finite gains in ±12 dB and integer balance −100…100 are accepted; booleans, unknown keys, paths and commands are rejected.
- `audio.json` is private (0600 on Linux), atomically replaced and flushed. IPC failure cannot acknowledge/save a change; disk failure sends the previous curve back. The native process validates band count/gains/balance again and publishes the accepted settings. A save is not proof of audible hardware output.
- Reconnect sends saved settings before processing projection audio. UI writes are serialized and incoming settings polls wait while edits are pending. Presets and Restore send complete named curves together; manual band changes are labeled Custom.
- Peaking bands use Q 1.4, 15 ms coefficient/balance transitions, channel-isolated state and signed-16-bit peak bounds. Partial PCM frames are retained between packets. Only our native projection streams are processed; these commands neither start playback nor modify arbitrary OS streams.

## Independent hotspot provisioning

- The installer is a local CLI, not an additional HTTP action. Its default check is read-only. `--apply` creates only the fixed `hudiy-recreation-car` profile bound to `wlan0`, as the current desktop user, with autoconnect off; it never activates or restarts Wi-Fi. Existing valid settings/profile return unchanged. First-time setup refuses a running app, duplicates, missing counterparts or mismatches.
- Generated WPA2/RSN/CCMP credentials travel through NetworkManager D-Bus, never shell interpolation, argv or output. New IPv4 shared settings use 192.168.12.1/24, receiver port 5277 and no default route from the car profile. User permission and the actual regulatory country remain prerequisites.
- A private setup lock serializes CLI runs. New 0600 settings are flushed and atomically published without replacement; existing files/symlinks cannot be overwritten. Failed settings saves attempt rollback only for the exact newly created UUID. Uncertain D-Bus outcomes and rollback failures require state inspection before retrying. No Polkit policies, system privilege grants or external backend rules are added.

## Fresh Pi installer privileges

- The installer runs as the ordinary desktop user on a 64-bit Bookworm/Trixie Pi desktop. Read-only checks run no installation commands; active car-app installation is refused. Package installation and a fixed system helper request sudo; the runtime/backend remain unprivileged.
- The system helper targets exactly the invoking SUDO_USER with a regular-user UID, and only the fixed dialout/video/plugdev groups, Bluetooth/oFono units, a panel-brightness udev rule and optional raspi-config desktop autologin. Standard distro Android USB rules are installed; no new broad D-Bus/Polkit grants or HTTP privilege endpoints are added.
- User WirePlumber configuration selects oFono for HFP in the version-appropriate format. Changed configuration gets timestamped backups. System and graphical startup selection occur only after successful builds/tests. No automatic reboot, display/audio restart, Wi-Fi activation, pairing, playback, call or ECU action is performed by setup.
- Official user-private Node ARM64 downloads are bounded, SHA256-checked against the official HTTPS manifest, and extracted with path/link/type/size bounds before execution. This is integrity verification, not an independent signature audit. Existing system Node remains available unchanged.
- Source bootstrap uses only the fixed project remote/main; existing dirty/foreign checkouts and symlinked installation targets are refused. Build commands run without sudo and use npm's lockfile and the pinned native dependency. An install lock prevents concurrent setup runs. External backend/cloud rules remain unchanged.

## Audio worker and diagnostics

- Native audio sinks and DSP are owned by a dedicated Qt worker. PCM delivery uses a locked, bounded mailbox rather than unbounded event payloads. The 1 MiB packet limit, fixed formats, independent channels, whole-frame overload eviction and generation resets prevent malformed input or old sessions from growing memory indefinitely or interleaving channel samples.
- Sink recovery creates only our channel's output, at most once per five seconds while active. It does not restart OS services, change devices selected by the user, start phone playback or issue calls. Current backlog warnings clear after recovery; cumulative dropped-byte and overflow counters remain visible.
- Existing GET projection/status responses now include `audioChannels` and `maximumAudioFeedGapMs`. Per-channel fields contain only active/state/error flags and received/written/queued/dropped/high-water/overflow/underrun counts. Neither raw PCM nor phone identifiers are exposed by these diagnostics; snapshots are copied before returning to callers.
- No new action endpoint, privilege, firewall change or external/cloud backend rule is needed. The explicit developer stress probe accepts only null-sink names and is excluded from normal CTest so automatic setup does not select physical playback.

## Custom OBD dashboard — 24 October 2026

- GET `/api/obd-dashboard` exposes bounded definitions, layout and revisions. POST accepts exactly `revision` and `config`, at most 16 KiB. Config contains at most eight sensors and 16 non-overlapping tiles in a four-by-eight logical grid; all source references, field sets, modes, identifiers, scales, intervals and coordinates are validated. Conflicting revisions return 409, invalid input 400, unavailable/failed storage 503. Loopback Host/Origin/JSON protections remain in force; the other action endpoints retain their 4 KiB limit.
- Device persistence is enabled only by our native application. `custom-obd.json` uses the existing private atomic/fsync storage helper. Definitions and layout persist; readings, bounded history, fuel integration and performance estimates remain session memory. Separate mapping revisions prevent position/title/view edits from invalidating sensor data. Browser preview storage is labelled; failed device saves are never silently acknowledged as browser-only success.
- POST `/api/obd-formula` accepts only a validated sensor and optional exact-length hex sample, at most 4 KiB. It performs no adapter I/O. Arithmetic ASTs allow only A–H, bounded numeric constants and `+ - * / // % & | ^` plus signs/parentheses, with 96 characters, 48 AST nodes and finite bounded intermediates/results. No eval, imports, calls, attribute access, powers or shifts are accepted.
- New vehicle requests are only `01` plus a two-digit PID, `22` plus a four-digit data identifier, and `03` for stored trouble codes. Optional validated 11/29-bit CAN headers use fixed ATDPN/ATSH operations on matching active CAN protocols and restore the default diagnostic header before ordinary reads. The worker selects at most two due custom reads per standard polling pass, uses 1–60 second minimum intervals, and reads codes at most every 30 seconds when selected. Unselected custom readings are removed. Responses are bounded and checked against the requested service/identifier. Fault clearing, arbitrary CAN messages, actuator control and ECU security access remain unavailable.
- Missing, stale and disconnected values do not become zero. Disconnect clears custom values, derived data, DTCs and history. Acceleration/run estimates reject invalid/gapped/implausible samples. Range needs explicitly configured tank litres, percent fuel level and L/h fuel rate plus 0.1 km of valid samples; invalid/gapped inputs reset integration. These are session estimates, not OEM range/performance guarantees.
- No additional package, network listener, privilege, cloud backend rule or authentication provider is introduced. Local simulator/browser checks do not establish powered-vehicle or on-Pi acceptance. See CUSTOM_OBD.md for the user workflow and verification limits.


## Configurable OBD diagnostic logging — 24 October 2026

- GET `/api/obd-logs` returns bounded session/status/settings/coverage data; GET `/api/obd-logs/{id}/preview` reads at most 64 KiB and returns the last 40 complete events. GET with `jsonl` or `csv` returns a fixed attachment after recording stops. Session IDs must match the generated timestamp/random-hex format; no caller path is accepted. - POST `/api/obd-logs` retains the Host/Origin/JSON checks and 4 KiB body ceiling. - Settings validate exact boolean fields and integer ranges: scan 1–30s, samples 1–60s, fault codes 10–300s, freeze/monitor/info refresh 10–600s, session 1–64 MiB, total 16–1024 MiB, and 1–100 sessions. Session size cannot exceed total size. Settings persist privately and capture choices freeze per session. Automatic mode applies to future connection attempts; manual mode remains available. Reducing quotas does not delete/hide existing recordings. Defaults are manual and all capture categories enabled.
- Recording uses the existing single ELM connection. New read requests are only Mode 02 plus a two-digit PID and fixed frame 00, Mode 06/09 plus a two-digit identifier, and Mode 07/0A code reads. Existing validated Mode 01/22 requests remain. Support bitmaps bound discovery; at most one extra request is scheduled per normal polling pass and minimum configured interval. - Private JSONL sessions record timestamps, definitions, capture settings, raw read/setup exchanges, numerical/structured samples, fault responses and connection errors. New startup marks unfinished sessions interrupted without erasing data. A sudden power cut can lose the last buffered interval.
- Quotas refuse/stop recording visibly; no automatic deletion occurs. Exports are serialized and bounded to 64 MiB input / 128 MiB CSV text, with a separate export-folder quota. Textual spreadsheet formula prefixes are escaped; numeric readings remain numeric. Preview/schema validation and plain React text rendering prevent log text from becoming executable markup. Symlinked storage/export targets and unrecognized session IDs are refused.
- Vehicle-information capture can include VIN/calibration identifiers; raw recordings and exports remain private/local and are excluded from publication. No new package, HTTP listener, privilege, external backend or cloud rule is needed. See OBD_LOGGING.md for exact scope and remaining physical-hardware acceptance.

## Android Auto automatic connection

The existing loopback `projection-settings` action accepts `autoConnect` only as a boolean and saves it atomically in private `projection.json`, separately from `autostart` (foreground opening). A save failure restores the previous native options and does not apply a new retry policy. Older preferences default to automatic admission, matching previous USB behavior. Native status publishes `connectionAllowed`, `automaticConnectionAllowed` and `sessionStarting`; missing status prevents automatic Bluetooth attempts. The switch does not terminate an active session. Quit pauses admission until a manual request or an Off/On change; unrelated settings saves do not undo Quit.

Bluetooth preferences migrate the earlier addresses-only object to bounded `addresses` plus `manualPhones`, preserving explicit manual-phone opt-outs. `/api/bluetooth` includes the effective reconnect selection. One paired recognized phone can be the automatic wireless default; multiple phones require explicit selection, and ELM327/audio sinks are excluded from that default. Per-device Bluetooth selection remains independently configurable. Android Auto retries target one eligible connected paired phone or its existing RFCOMM handoff, at most every 30 seconds; they do not pair, trust, disconnect Bluetooth devices, change the network, initiate calls or open the projection screen. Service startup failures retry through owned workers. No new endpoint, cloud rule, package dependency or permission is required. Native build and end-to-end boot/range/USB/Wi-Fi acceptance remain pending while the Pi is off; see the README checklist.
