# Backend rules

- GET /api/bluetooth exposes only bounded BlueZ device names, addresses, paired/connected flags and adapter/scan status. The Pi worker uses one powered adapter, validated BlueZ object paths and at most 128 devices. No pairing keys, D-Bus paths, advertised payloads or contacts are written to preferences/logs/cloud storage. Only explicitly selected automatic-reconnect addresses are privately persisted as described below.
- bluetooth-scan and bluetooth-scan-stop accept only the action field. Discovery is an explicit, owned BlueZ session, bounded to 30 seconds after the latest request and released on stop/shutdown; it does not alter Powered, Discoverable, Pairable or Trust settings.
- bluetooth-remove accepts only action, address and confirmed: true. The address must be an uppercase MAC currently paired on the selected adapter; the service revalidates it before RemoveDevice. The UI names the device in a confirmation dialog and Cancel/Escape performs no mutation. This action removes pairing information and may disconnect the device; a real user's device is never removed for automated validation.
- bluetooth-pair-menu accepts no arguments and dispatches only the fixed documented pairing_menu action to the existing installed Hudiy agent. It cancels pending projection-opening intent. This does not register another Bluetooth agent, bypass PIN confirmation, accept a caller-supplied native action, or grant trust automatically. Existing Host/origin, loopback and request-size restrictions apply.
- bluetooth-media accepts only action and operation (toggle/next/previous). It revalidates exactly one connected, paired device's addressed MediaPlayer1 on the selected adapter before invoking only Play/Pause/Next/Previous with a three-second D-Bus timeout. Caller-supplied device paths, seek positions, files, URLs and arbitrary method names are rejected. Unavailable/ambiguous players fail without a device action. No extra system permissions are required.
- Media subscriptions now accept the documented Android Auto and A2DP sources. Switching source or receiving no active source clears old native metadata/artwork. Quitting Android Auto preserves independent Bluetooth metadata; runtime disconnect clears its native cache. The independent BlueZ fallback remains available only while its paired addressed player stays connected. Playback controls on the Bluetooth page target its AVRCP player even while stopped. Bluetooth starting preserves the recreation's current view unless native pairing was explicitly requested or Android Auto is visible.

- Bind only to 127.0.0.1, port 8766 (or explicit development port 4173).
- Accept Host only for localhost/127.0.0.1 on the supported ports. Reject foreign browser origins.
- JSON action requests have a maximum body of 4096 bytes and a five-second socket timeout.
- Serve files only from the resolved frontend build root. No arbitrary paths, shell commands, credential storage or public network endpoints.
- OBD transport allows /dev/ttyUSB*, /dev/ttyACM*, /dev/rfcomm*, COM ports, and a loopback TCP simulator. Commands are restricted to ELM initialization and supported read-only Mode 01 PIDs; no diagnostic-code clearing or vehicle control.
- Disconnect clears live measurements. Demo telemetry must be labeled. Phone connection and projection visibility come from the documented Hudiy API when the projection host is enabled. Visibility is not proof of an active session while projection is hidden.
- Android Auto is rendered by the installed licensed Hudiy runtime. The bridge is enabled only by the trusted launch environment (`HUDIY_PROJECTION_HOST=1`) and connects only to 127.0.0.1:44405. API frames are bounded to 1 MiB; invalid or disconnected sessions clear live status and reconnect with a delay.
- Projection actions accept only Android Auto USB, Wi-Fi, resume, quit, allowlisted recreation routes, and current Android Auto/Bluetooth play/pause/next/previous controls. Media controls require a reported supported media source. HTTP callers cannot supply arbitrary Hudiy actions, ports, hosts or keys. A successful request means it was sent to Hudiy; the runtime's subsequent visibility status determines whether projection actually opened.
- application-quit accepts only the action field and requires the trusted Pi projection-host environment. It dispatches the fixed quit_hudiy command once, cancels pending projection opening/USB retries, and prevents recreation navigation from reopening the runtime during shutdown. The owning host exits only after the runtime disconnects, then ends its own backend. An ignored request times out after 15 seconds while the runtime remains available, preserving the service and permitting retry. Quit does not reboot/power off the Pi, change autostart, erase saved settings, or accept process IDs, commands or paths. Browser development outside the Pi host returns 501 without closing unrelated programs.
- The bridge refreshes projection/media/navigation/phone subscriptions and the frontend checks metadata at the configured music interval (integer 1–60 seconds, default 5). USB recovery checks remain every five seconds. Metadata and PNG/JPEG album art remain in memory and clear on runtime disconnect or a change away from the current supported media source. Reported call state/name/number are exposed locally; call audio and arbitrary images are not exposed.
- Projection preferences accept boolean autostart/taskbarVisible/darkMode and an exact dayNight choice of Common, Day or Night. They are saved atomically in the user's private local projection.json. Explicit appearance changes require an available runtime that is not closing; day/night additionally requires negotiated API 1.3 or newer. Only fixed documented messages 37 (native dark mode) and 50 (Android Auto mode enum) are sent; no caller-supplied message IDs/actions are accepted. Saved explicit choices are resent on native API reconnection. Legacy preferences leave native appearance untouched until explicitly selected. Saving precedes the command, so save failure changes no native appearance. Send failure restores the old saved options and attempts to resend the previous explicit native choice; errors retain the old in-memory options. Native commands have no appearance acknowledgement; saved/sent state must not be described as visual proof. Automatic connection remains enabled for background data; the bridge controls whether connection brings projection forward. Manual Resume overrides automatic-opening-off for that session.
- Layout application uses a bounded, explicit restart request. The host asks the installed runtime to quit through its documented API, waits for disconnection, changes only the documented projection/overlay geometry, then starts it again. No caller-supplied scripts or process IDs are accepted.
- Linux audio-volume accepts 0–100 and invokes wpctl without a shell. Phone call controls require the installed Pi HFP service; phone-refresh is available through PBAP. Native pairing-menu dispatch and live Bluetooth mutations require the installed Pi host, and return 501 outside it. Projection returns 501 outside the Hudiy host and 503 when its API is unavailable.
- Static responses set CSP, nosniff and no-referrer. Theme preferences stay in local browser storage; physical brightness and Pi layouts use private backend files. Selected audio files use local blob URLs.

No external Firebase/Supabase/backend authorization rules exist or need changing. These are the newly introduced local service rules.

- GET /api/display reads the existing physical backlight. display-brightness accepts only action and an integer brightness from 5 to 100. The trusted Linux Pi host selects exactly one kernel backlight, uses existing user write permissions and saves only the percentage in private, atomic brightness.json. No caller paths, sudo, permission changes or shell execution are accepted. Startup reapplies the saved percentage; actual values are rounded to the hardware's range. This controls the whole physical panel, including Android Auto; theme contrast remains separate.
- GET /api/obd-settings exposes only the native OBD transport/address/channel and paired Serial Port devices. obd-native-settings accepts only a currently paired Serial Port address and integer channel 1–30, preserves other native configuration, writes atomically and requests the existing bounded runtime reload. It refuses changes during a reported call and rolls back configuration if reload scheduling fails. BLE-only adapters are not implemented. The hudiy OBD transport delegates only six supported read-only Mode 01 PID requests to the installed runtime, with correlated responses and a three-second timeout; it does not own another RFCOMM socket or reset the adapter. NativeOBDConnected must be true before polling; no live vehicle readings are claimed from configuration alone.
- The Pi backend starts an automatic OBD monitor independently of phone projection and optional radio audio. It checks the installed runtime's actual availability/nativeOBDConnected every five seconds and starts the existing six read-only sensor queries only when connected and not shutting down. Poll failures retry at most every 30 seconds while the native connection remains available. A disconnect clears values, history and timestamps; returning native connectivity starts a fresh history. Manual obd-disconnect suppresses automatic polling for the current service session; manual hudiy connection enables it again, while a selected serial/USB/simulator connection takes precedence. Backend startup restores native automatic monitoring. GET /api/status reports obd.automatic; this means monitoring is enabled, not that a real adapter or live reading has been verified. No pairing, arbitrary vehicle commands, audio dependency, new permission or additional RFCOMM owner is introduced.
- Bluetooth metadata has an independent, read-only fallback from exactly one paired, connected addressed BlueZ player. Titles/artist/album are bounded to 512 characters and timing to one day. Android Auto has priority; old native artwork is retained only for the same title/artist/album. Disconnection or ambiguous players clear this fallback.
- bluetooth-connect accepts only action/address for a currently paired device and invokes the fixed BlueZ Connect method. bluetooth-disconnect also requires confirmed: true, refuses a reported active phone call, and disables that device's automatic reconnect before Disconnect. bluetooth-autoconnect additionally accepts only boolean enabled. At most 16 chosen paired addresses are saved privately in bluetooth-connections.json; no keys, contact data, arbitrary profiles or D-Bus paths are accepted. Background reconnect is limited to one attempt per device every 30 seconds, never pairs devices or changes trust, and revalidates pairing. A request being accepted does not prove the device connected; the live connected flag does. Manual connection uses a three-second timeout.
- Phone controls use the existing oFono HFP modem matching exactly one connected, paired BlueZ device. The worker loads calls on modem attachment and monitors scoped call signals; up to 16 calls are kept only in memory and cleared on disconnect. phone-call accepts only a normalized 3–20 digit number (optional leading +) and confirmed: true, and refuses an existing call. The UI shows the actual number before confirmation. phone-answer and phone-end accept no arguments and target exactly one valid current call; Answer requires incoming state. phone-microphone accepts only boolean muted and requires one active call and an existing oFono Muted property. No arbitrary modem/call paths, methods, USSD strings, multiple-call hangup, automatic dial or audio recordings are accepted. Device identity/current calls are revalidated at action time; each D-Bus request has a three-second timeout. Calling availability is live HFP availability, not proof of completed calls or audio routing. Existing system permissions suffice.

- Connect USB and Resume may recover a stale, uniquely identified Android Open Accessory device. Only USB vendor 18d1 with accessory product IDs 2d00/2d01/2d04/2d05 is eligible. The service validates the character device and bus/device numbers, resets at most once per 15 seconds, and uses existing device permissions without sudo, USB hub resets or caller-supplied paths. An active session is resumed without resetting. Quit explicitly clears live media/navigation and does not automatically reconnect; a subsequent manual Connect/Resume starts recovery.
- GET /api/phonebook serves local contacts, favorites and up to 100 recent call-log entries from the single connected, paired Bluetooth phone advertising PBAP. Contacts are obtained via documented BlueZ OBEX methods, independently of Android Auto USB. The service monitors connection state every five seconds, refreshes phonebooks at the configured interval (integer 5–3600 seconds, default 60) or on explicit Refresh, and the UI checks its memory cache every five seconds. The first download after connection is immediate regardless of time since boot; later refreshes use the selected interval. Transfer duration and the connection check can delay completion. Contact-sharing permission on the phone remains required.
- Phonebook transfers are limited to 2 MiB, 1000 contacts, 100 favorites and 100 call-log entries. Only names, up to eight normalized phone numbers and call timestamps are retained. Private temporary transfer files are removed after parsing; cached data stays in RAM and clears on detected Bluetooth disconnect. No contacts are saved in browser preferences, telemetry, logs or cloud services. POST phone-refresh accepts only contacts/favorites/call-log views. Selecting a contact opens the dialpad; calling then requires the separate number confirmation and available HFP service.
- The five-second phonebook connection check also verifies its own OBEX session still exposes PhonebookAccess1. If obexd removed it while Bluetooth stayed connected, the worker clears its RAM cache, removes only its own old session and creates a new PBAP session for the same validated paired phone. A recreated session requests immediate downloads. It never adopts or removes other clients' sessions or restarts Bluetooth/oFono.
- GET /api/wireless exposes hotspot enabled state, a bounded SSID and band, never its password. wireless-hotspot accepts only boolean enabled and confirmed: true in the Pi host, refuses active calls and uses the existing bounded Hudiy reload. Enabling validates the existing protected SSID/password, selects the system adapter, 5 GHz and the fixed private hotspot gateway; unrelated configuration and existing credentials are preserved. Native OBD/wireless edits share a lock to prevent concurrent updates losing fields. Writes roll back if restart scheduling fails. This does not alter NetworkManager connections, firewall, OS permissions or register new agents. Enabling the hotspot can interrupt the Pi's existing Wi-Fi client connection. The native runtime stops its hotspot on Quit. Actual wireless projection requires a phone connection and cannot be inferred from saved settings.
- GET /api/audio-route exposes selected receiver address, paired A2DP receiver names/status and observed routing status. audio-radio-output accepts only a currently paired A2DP sink address or an empty selection, and refuses active calls. Phones advertising PBAP are excluded from receiver choices. Only the address is saved atomically/private in radio-output.json; no audio is recorded, no playback is started, and saving does not pair or connect a receiver. Existing per-device Bluetooth automatic reconnect can be enabled separately.
- With a saved connected receiver, a five-second audio worker locates its unique BlueZ sink and the existing hudiy_equalizer_sink/echo_cancel_sink chain. Only playback streams sharing those sinks' nonempty node.link-group ownership are moved with bounded, argument-array pactl calls. The echo playback stream goes to the receiver, equalizer output to echo sink and the default sink remains the equalizer. Missing/ambiguous receivers or chain nodes cause no route mutation. IDs/names come from current local audio state; callers cannot supply them. Each command times out after three seconds, parsed output is size limited, and a later poll must observe the desired chain before routed becomes true. Clearing the selection stops managing the route; it does not disconnect the receiver or reset unrelated audio state. No audible-radio success is claimed until actual hardware is tested.
- Reported phone battery/signal come from the Hudiy phone subscription. Current-call identity/state is supplemented by the matched oFono HFP service when available. Controls are enabled from that service's actual availability and current call state; they do not imply a real call/audio test has passed.


- If a manual reconnect falls within the USB reset cooldown, one delayed retry runs from the five-second checker. Quit or Dashboard cancels pending reconnect intent. No background reconnect is scheduled after an intentional Quit.
- Manual Resume uses the last explicitly requested connection transport, or the saved enabled car hotspot after host startup, when no Android session is live. It sends only the fixed Wi-Fi connection action for wireless recovery. A detected Android USB accessory takes priority and retains the existing bounded USB recovery. A live session uses the fixed projection-resume action. Wi-Fi and USB connection requests share the connection lock; this does not change automatic-opening preferences or reconnect automatically after intentional Quit.

- Pinned taskbar shortcuts may open only explicitly allowed recreation screens, such as Contacts, Theme or Gauges. Each route dispatches the same fixed hudiy_recreation action and increments its local route revision; it cancels pending projection-opening intent while retaining background phone/media data. Routes never accept URLs, shell commands or arbitrary native action names. Non-string and unknown route operations are rejected.
- Layout preferences contain only known shortcut IDs and validated ordering lists. In the Pi host, POST layout-settings saves the complete validated layout atomically to the user's private local layout.json file (0600), and the existing status endpoint synchronizes the two web views. JSON requests retain the 4096-byte limit; unknown IDs, duplicate items, malformed categories and missing Dashboard/Applications/Android Auto shortcuts are rejected. The standalone desktop preview uses local browser storage. No contact names/numbers, arbitrary scripts, network destinations or images are stored in layout preferences. No new permissions or external backend rules are needed.

- Private JSON saves flush/fsync the temporary file before replacement and fsync its parent directory on Linux before acknowledging success. Browser edits wait for host layout hydration; stale status responses cannot overwrite a newer local edit. Catalog upgrades append the two new known settings entries while preserving previous order.
- POST /api/action with action refresh-settings accepts only an updates object containing musicRefreshSeconds and/or contactsRefreshSeconds within the bounds above. Boolean, fractional, string and out-of-range values, extra fields and caller-supplied paths are rejected. Values are stored in ~/.local/share/hudiy-recreation/updates.json (0600), applied live and loaded before worker startup. GET /api/status includes updates. Host/origin restrictions and the 4096-byte body limit remain in force. No external backend permissions are needed.
